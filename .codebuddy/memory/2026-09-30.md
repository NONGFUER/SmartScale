# 2026-09-30

## 排查并修复"设置里的设置重启后失效"

**现象**：设置页（价格输入 / 按斤显示 / 网络模式）改了以后重启又变回旧值。

**根因（有实测证据）**：`/home/sjwu/.config/SmartScale/AppSettings.ini` 属主是 **root:root**（`-rw-rw-r--`），以 sjwu 身份运行时 `QSettings::sync()` 静默失败（`echo >>` 直接报"权限不够"）→ 内存值生效、磁盘值不变 → 重启回落。

**root 属主从哪来**：`apply_update.sh` 会 `sudo -n` 自我提权到 root；当它探测不到 systemd service 时走 `nohup "$APP_BIN"` 兜底，于是**应用以 root 启动**。由于 `AppPaths` 已把家目录纠正到 `/home/sjwu`，root 实例就把配置/缓存写在了用户家目录下（实测还留下 `root:root` 的 `build/AI/rec.onnx`、`cache/smartscale/embedded`、2 张 `ingr_images/*.jpg`，时间戳均为 09-29 17:51）。本机 `smartscale.service` 未 enable（且 `ExecStart` 指向已不存在的 `start_app.sh`）⇒ 走的就是这条兜底路径。

**已做的修复**：
1. 现场修复（sudo chown 回 sjwu）：`AppSettings.ini`、`.cache/smartscale/embedded`（递归）、2 张 root 属主图片、`build/AI/{rec.onnx,ppocrv5_dict.txt}`；复查这三棵树已无 root 属主文件。
2. 代码 `src/utils/AppPaths.{h,cpp}`：新增 `adoptOwnership(path)`（递归、仅 `euid==0` 且家目录已纠正时生效）与 `adoptAppDataOwnership()`（启动时扫 `configDir()/cacheDir()`）；`app/main.cpp` 在 `retireStaleRootData()` 之后调用。
3. 代码 `AppSettingsService`：新增私有 `persist()`（`sync()` + `adoptOwnership(fileName())`），6 个 setter 改走它 —— 覆盖"root 实例运行期间新写的文件"；构造时若文件不可写打 qWarning 明确提示属主问题；头文件里过时的 "UserScope / AppSettings.conf" 注释已改正为显式 `AppSettings.ini`。
4. `scripts/apply_update.sh`：新增 `launch_direct()`，root 兜底拉起时用 `runuser -u <APP_DIR 属主> -- env HOME=<owner home>`（HOME 必须一起改，否则非 root 实例的 `AppPaths` 会按 HOME=/root 解析）；成功路径与回滚路径都用它。注意脚本改动**第二次 OTA 才生效**，存量设备靠第 2、3 条的二进制自愈逻辑。

**验证**：`read_lints` 全绿；`bash -n apply_update.sh` 通过；`test -w AppSettings.ini` 通过。未编译（AI 不执行 make）。

## 补充：`<APP_DIR>` 侧（AI / keyboard_styles / 二进制）也会被 root 写走

用户追问 `build/keyboard_styles/` 升级后是否也会变 root —— 之前的修复**没覆盖** `<APP_DIR>`（`adoptAppDataOwnership()` 只扫 `configDir()`/`cacheDir()`）。已补齐：

1. `src/utils/EmbeddedAssets.cpp`：新增 `adoptAndReturn(dir)`，`resolveDir()` 的**每个成功返回分支**（①设备目录齐备、②③释放到设备/缓存目录）都先 `AppPaths::adoptOwnership(dir)` 再返回 —— root 实例释放的内嵌资源（`AI/`、`keyboard_styles/`）写好即归位普通用户，非 root 无副作用。
2. `scripts/apply_update.sh`：新增 `adopt_owner()`（chown -R 到 APP_DIR 属主，APP_DIR 属 root 时跳过），在①资源目录同步成功后、②二进制替换 `chmod 755` 后各调用一次 —— 覆盖 `cp`/`cp -a` 造成的 root 属主。
3. 复核现场：`build/keyboard_styles/**`、`build/appSmartScale`、`build/AI/**` 当前均 sjwu:sjwu，`sudo find build -maxdepth 4 -user root` 为空（AI 两个 444 文件是此前手工 chown 的，`QFile::remove` 只需目录写权限，故 444 本身不影响后续覆盖）。

**属主问题的完整覆盖面**（后续排查照这个清单看）：`~/.config/SmartScale/*`、`~/.cache/smartscale/*`、`<APP_DIR>/{AI,keyboard_styles,appSmartScale}`。

## 结论：`smartscale.service` 确认为历史残留（用户判断正确）

- `start_app.sh` 在 commit `c731a1b`（"fix: 修复数据库路径及优化水印卡片布局"）被删除（15 行：`sleep 5` + `QT_QPA_PLATFORM=xcb` + `cd build && ./appSmartScale | tee /tmp/smartscale.log`），此后 unit 永远起不来；现状 `disabled` + `inactive`，全盘也搜不到该脚本。
- 真正的开机自启是 **`~/.config/labwc/autostart`**，内容仅一行 `<APP_DIR>/appSmartScale &`（2026-04-25 写入，labwc 以 sjwu 身份执行）。本机 `APP_DIR=/home/sjwu/SmartScale` 顶层没有二进制，故本机不自启；设备上该路径就是 OTA 替换的二进制，属正常。
- **重要推论**：服务探测永远失败 ⇒ `apply_update.sh` 每次 OTA 都走 `nohup` 兜底（root）⇒ 我加的 `launch_direct()` 是必需修复而非加固；上一轮"建议修好服务并 enable"的说法已撤回（enable 反而会和 labwc autostart 抢启动）。
- 附带：`~/.config/labwc/autostart` 之前也是 root 属主（已 chown 回 sjwu）。

**顺带发现**：`/etc/systemd/system/smartscale.service` 的 `ExecStart=/home/sjwu/SmartScale/start_app.sh` 在该机器上不存在、服务也未 enable，所以本机是手动跑 `build/appSmartScale`；真机部署若也缺 `start_app.sh`，OTA 就会一直走 root 兜底路径。
